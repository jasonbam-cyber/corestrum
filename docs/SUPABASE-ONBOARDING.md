# Customer-owned Supabase bridge: installation and acceptance

The first integration is a developer-assisted, read-only installation in a customer's staging project. The customer's database remains the source of truth. Waypoint receives a narrow projection of a requested record; it does not receive a Supabase administrator key, database password, SQL access, arbitrary table access, or a general API proxy. AI execution, writes and billing are not enabled by installing this bridge.

## What the customer does

1. Give the operator the Supabase **project reference** and the downstream account UUIDs approved for the pilot. These are identifiers, not credentials. The operator provisions a dedicated customer runtime pinned to that project. Sign in with MFA and select your approved workspace.
2. In the onboarding page, enter the allowed account UUIDs and create the installation manifest. It contains the customer UUID, installation UUID, project reference, grant version, `records.read` capability, account allowlist and an Ed25519 **public** key. The private signing key stays inside your dedicated runtime. Copy the manifest to `manifest.json` in your local copy of the installation kit.
3. Review `bridge/supabase/migrations/*_waypoint_bridge.sql` and apply it **only to your chosen staging project** through your normal reviewed migration process. It creates an unexposed `waypoint_private` schema and a dedicated `waypoint_bridge` role. It fails if that role/schema already exists; it does not adopt or overwrite another integration. Never add this schema to Supabase's exposed schemas.
4. Run `bun run bridge:grant manifest.json > grant.sql`, inspect the generated project/account/public-key binding, and execute `grant.sql` in that same project. Reinstallation is deliberately not an upsert. Revoke and remove the old binding through a reviewed customer change before replacing it.
5. Map your approved application fields into `waypoint_private.records(id, account_id, title, status, version)` using your own server-side application/migration process. This table is an explicit integration projection, not a copy of your whole database. `id` and `account_id` are UUIDs; `title` is at most 500 characters; `status` is `open` or `closed`; `version` is a positive integer. Increment version whenever exposed data changes. Use a transaction or customer-owned trigger so deletions, scope changes and opt-outs propagate. Keep private notes, credentials, financial details and unneeded personal data out. An application-specific mapping cannot be inferred safely from an arbitrary SaaS schema; it is reviewed with the first customer.
6. Activate a login for `waypoint_bridge` with a fresh random password using your existing secret-management workflow. It must retain NOSUPERUSER, NOBYPASSRLS, NOINHERIT, NOCREATEDB, NOCREATEROLE, NOREPLICATION and **no role memberships**. Store its TLS connection URL as the custom Edge Function secret `BRIDGE_DATABASE_URL` **inside your Supabase project**. Use the restricted role in the connection URL, including Supavisor's project suffix when applicable. Do not use the automatically injected administrator database URL or a service-role key. Do not paste this secret into Waypoint or send it to the operator.
7. Deploy `bridge/supabase/functions/waypoint-bridge` and its locked dependencies to that project. The checked-in function configuration disables Supabase's user-JWT precheck because this function authenticates its own asymmetric installation JWT. The handler requires a valid signature, exact issuer/audience/customer/project/install/grant, short expiry, body hash and unique nonce **before** reading data. Do not deploy a skeleton handler with the precheck disabled. Set `BRIDGE_DATABASE_URL` through Supabase's secret UI or a local protected env file; never put a password on a shared command line. CLI commands should explicitly name the reviewed `--project-ref`.
8. Click **Verify project and grant** in Waypoint. Discovery must match the manifest exactly. Then prove a read using one approved record UUID and account UUID. Verify an unapproved account and random record are denied, disconnect on both sides, and verify access stops. Use test records, not production PII, for this acceptance pass.

The onboarding page prefills the active installation ID after preparation, and shows the result above the steps. Viewer accounts can inspect status; only owners can prepare, verify, read or disconnect. No browser-supplied tenant or project changes the routing destination.

## Independent database protections

All three private tables have ENABLE and FORCE ROW LEVEL SECURITY. The bridge role can select only the binding and the five record fields, and insert only the nonce ledger. RLS filters records by the approved downstream account allowlist and active grant even when a query omits its own filter. The role cannot edit the installation, insert/update/delete application records, read nonce history, assume another role or bypass RLS. Requests use constant, parameterized SQL. There are no SECURITY DEFINER functions or privileged views in the kit.

On startup and every request, the bridge checks role flags, role memberships, extra application-table privileges and callable application SECURITY DEFINER functions. PostgreSQL's `PUBLIC` grants can otherwise give a newly created role unexpected access. If this check fails, onboarding stops. The customer must review/remediate those preexisting privileges as an application change; Waypoint must not silently revoke grants that existing users depend on. Keep this permission check in the deployed handler.

Each request JWT expires within 30 seconds. The receiver admits at most 60 seconds and rejects reused nonces with a database primary key. Six concurrent attempts using one token are tested to admit exactly one read. TLS binds discovery to the pinned project endpoint; the valid request signature proves that the installed public key matches the runtime key. This is not arbitrary URL discovery. Custom domains, self-hosted Supabase, multiple installations per project and write capabilities are outside this initial adapter.

## Revoke, rotate and remove

Disconnect in Waypoint to block new calls, fence in-flight responses and remove its current encrypted signing-key reference. In Supabase, atomically set `active=false` and increment `version` in `waypoint_private.installation` to reject already issued requests. Re-enable is not a way to revive old approval or key state. Create a new installation/key and bind it through the reviewed customer process. Rotate the restricted DB password locally in Supabase and update its Edge secret without exposing it to Waypoint. Pause the integration during credential recovery; do not fall back to a broader credential.

The customer owns projection retention and the nonce cleanup job. A privileged scheduled job may delete `requests` with `expires < now() - interval '5 minutes'`; retain separate audit evidence according to policy. The bridge role itself cannot delete the ledger. For full removal, revoke the grant/login and undeploy the dedicated function first, then remove the private projection/schema/role under the customer's normal backup/retention approval. Do not remove any app source tables. Platform encrypted backups can retain old key ciphertext; lifecycle/KMS controls must address that before production.

## Evidence and live acceptance

`bun run test:postgres` tests the migration, restricted-role permissions, real RLS, signed bridge reads, nonce persistence/concurrency, inherited privilege detection and provider-side revocation in a disposable local PostgreSQL cluster. `tests/production.test.ts` tests runtime isolation, scope binding, ciphertext binding, grant rotation, denied roles, egress and revocation. Deno checks the deployable Edge entry point using its committed lockfile. These do **not** prove a hosted Supabase deployment. The customer staging acceptance must additionally run Supabase security advisors, check actual role ownership/grants/SSL/pooler behavior, test their field mapping and deletions, verify logs contain no source data or credentials, and record project/function revision plus successful and denied reads.
